# BM1370 work targeting investigation

Status: protocol investigation and a guarded BM1370 driver rewrite, 7 October 2026. No physical chip selector or concurrent isolation is verified. The rewrite is described in [BM1370 driver rewrite](bm1370-driver-rewrite.md); its diagnostic switch defaults off. The paired a9 bench candidate is installed and its ordinary job/result path has real nonce/header evidence. No undocumented ASIC register write, new command format or clock change was used. The capability prototype still reports `independentWorkAssignment: false` and `workTargeting: "chain-broadcast"`.

The observed test board is a NerdQAxe++ with four BM1370 ASICs, originally reporting `v1.1.0-rc1-test1` and currently running the paired `5tratumFW-qa-diag-a9` candidate, with saved **500 MHz / 1130 mV**. Its exact PCB/regulator revision is unknown. That operating point remains unchanged during this bench; source defaults do not identify the PCB. The zero per-chip temperature reports are unavailable measurements. See [a9 validation](validation-a9.md) for the paired OTA and actual capture observations.

The evidence establishes an implementation gap and an unknown hardware mechanism, rather than proving that BM1370 isolation is physically impossible. A firmware signature, four sockets, distinct worker names or distinct returned ASIC indices cannot fill that gap. No reviewed source supplies a validated job-acceptance gate or addressed job format that preserves other chips' work.

Do not insert a chip address into the existing payload, reinterpret the Job ID/midstate fields as an address, or assume `0x21`/`0x31` selects a particular chip. An inserted byte changes the documented field positions, length and CRC. Turning off other cores or hiding their nonce responses also does not prove concurrent independent work.

The user requires a firmware-only solution, with the hardware unchanged. Published [QAxe++ CAD](https://github.com/shufps/qaxe/blob/be1a4a071def733a601a62b4fda3f3c5558c332e/nerdqaxe%2B%2B/nerdqaxe%2B%2B/nerdqaxe%2B%2B.kicad_pcb) shows one controller UART through the level translator to the ASIC chain, rather than four independently routed controller UART links. This source topology does not identify the unknown test PCB revision, and does not prove that an undocumented job acceptance gate is impossible.

The [offline capture checker](asic-capture-checker.md) now supplies source-exact TX validation, captured-format RX checksum validation and explicit header hashing. It still reports isolation and drain as unqualified. No new ASIC command or register write was sent during this investigation.

Simultaneous per-ASIC mining remains the active goal. The user reaffirmed that goal and requested a driver rewrite; the unfinished percentage-allocation draft was copied with SHA-256 checks to an ignored checkpoint and removed from the active source tree. It was never deployed. Percentage allocation remains a separately authorized fallback: select named pool slots for long consecutive blocks of actual mining time over a 1-, 6- or 24-hour cycle, with 24 hours as the default. Pauses and unavailable selected pools do not consume their allowance. This is whole-chain time allocation, not simultaneous per-ASIC mining. Its implementation and physical validation must be recorded separately; the preferred per-ASIC job/pool requirement remains unresolved.

## Version-rolling constraint

The pinned Nerd initialization programs `0xA4` with `0xFFFF`, corresponding to the ordinary rolling range `0x1fffe000` (bits 13–28). The work packet supplies a base version, and result reconstruction combines that base with the returned rolling bits. This is not evidence that the chip implements an arbitrary bitwise mask or safely isolates a different mask per outstanding job.

In [upstream issue #640](https://github.com/shufps/ESP-Miner-NerdQAxePlus/issues/640#issuecomment-4934362452), the maintainer reports testing a mask with a hole, `0x1f00e000`, and observing only the `0x0000e000` portion. [The final maintainer comment](https://github.com/shufps/ESP-Miner-NerdQAxePlus/issues/640#issuecomment-4950409788) leaves LCC/MazaCoin support unresolved. Accordingly, the first isolation test must use one common, already working rolling configuration for both jobs. It must not write a new mask. Smaller contiguous ranges, shifted ranges, masks with holes and disabling rolling require their own proof; none is qualified here.

For every captured nonce, check `(rolledVersion ^ baseVersion) & ~allowedVersionMask == 0` and preserve all coin-specific required bits. SHA-256d compatibility alone does not qualify a coin pair.

## Exact inputs for a bounded capture verifier

The verifier is an offline consumer. It must never send a UART command, register write, mining job or network submit. A proposed JSON capture contains:

- `captureVersion: 1`; exact firmware binary SHA-256; source revision; known board profile; nullable PCB revision; `asicModel: "BM1370"`; configured MHz/mV before and after; actual enumerated chip addresses and attribution mode. A reported profile count is insufficient to invent enumeration.
- Two immutable work records A and B: a distinct name; a canonical **76-byte Bitcoin header prefix** encoded as 152 lowercase hex characters (version, previous hash, merkle root, time, bits in normal serialized-header byte order); the allowed rolling mask; required version mask/value; ASIC ticket threshold; logical job generation; exact transmitted wire job ID and original packet hex. A and B differ in the merkle root, use the same base version/mask and have non-colliding live work slots. Never include credentials, coinbase secrets or an upstream worker identity.
- Ordered events with monotonic timestamps: `dispatch` records referencing A/B and the captured packet; `nonce` records with the complete CRC-valid response; and an `attribution` record documenting how decoded ASIC addresses map to indices. An intended target is a claim to compare with observed nonces, not proof.
- A named, source-supported candidate mechanism and its packet/register evidence **only if one is subsequently established**. The current value is unavailable. The verifier must not manufacture or execute a candidate.

Decode work IDs and nonces using the exact pinned driver mode. Do not reuse the response's low small-core bits as a chip selector. Reconstruct each full 80-byte header from the immutable prefix, decoded version and nonce; independently SHA-256d it; compare against both A and B and the configured ticket threshold. Reject bad CRCs, ambiguous/no-match work, disallowed version changes, unknown chip attribution and reused IDs without a known generation. Use the driver's byte-order rules; validate the decoder against offline known-answer vectors before interpreting a capture.

## Two-job isolation test and promotion gate

This is a test plan for separately authorized bench work, not a completed test or a flash instruction.

1. Preserve 500 MHz / 1130 mV, fan/safety settings and the working version mask. Confirm the actual four-chip enumeration and establish a normal baseline. No undocumented writes are part of this plan.
2. Record a broadcast negative control: send A normally, then send B normally. After documented pipeline drain, all four active chips should produce B results. This validates decoding and demonstrates why ordinary work dispatch is not isolation.
3. Once an evidenced targeting mechanism exists, repeat with A on the chain and B targeted to one chip. Untargeted chips must continue producing valid A results while the selected chip produces valid B results concurrently. Repeat each selected index, then change B to another distinct header on that chip and check that the other three remain uninterrupted.
4. Bound each steady measurement by a fixed duration and require enough independently verified results per chip to distinguish silence from isolation; 100 per chip is a useful initial collection target, not a statistical guarantee. Log the existing ticket threshold and expected result rate. Timeout, chip silence, cross-chip B results, invalid hashes or power/thermal faults fail the test. Pipeline results count only within documented dispatch/drain windows; never guess a drain time merely to discard contradictory results.
5. Extend successful two-job evidence to four simultaneous distinct headers, then clean jobs, reconnect/session generations, stale results and work-slot reuse. Preserve immutable result context until all possible responses drain. Verify that shared reset/pause/fault handling stops every logical child.

Only reproducible concurrent header/nonce evidence on the identified PCB and exact firmware can qualify per-chip dispatch. MUX admission must bind that evidence to the exact binary digest, physical identity, ASIC count/model and verified board revision; its private trusted registry remains empty by default. The present capability prototype and discovery report do not qualify.
