# Offline BM1370 capture checker

`tools/asic_capture_check.py` checks an existing capture file without opening a
serial port, contacting a miner, changing settings, or transmitting anything.
It is preparation for the evidence work in
[the work-targeting investigation](asic-work-targeting-investigation.md).
It does **not** qualify independent work assignment or enable a MUX core route.

```sh
python3 tools/asic_capture_check.py capture.json > report.json
python3 test/host/test_asic_capture_check.py
```

Exit status 0 means the supplied supported checks did not fail; 1 means a frame,
binding, candidate-header check failed, or a TX checksum could not be checked;
2 means invalid input or a file error. A successful exit never means response
CRC was observed on our QAxe, or drain behaviour, chip attribution, or isolation
was independently proved. JSON report version 2 separates captured-format CRC
validation from physical-device qualification; input capture version stays 1.

## Evidence available so far

The initial local audit on 7 October 2026 found no raw ASIC UART captures or
validated response CRC vectors in the repository's `test`, `docs`, and `.cache`
artifacts. Subsequently, independently reviewed primary evidence supplied five
published BM1370 frames from Bitaxe Gamma and S21 Pro captures. Their exact
bytes, origins and source lines are retained in
`test/host/fixtures/bm1370_captured_rx.json`, pinned to Mujina commit
`980128574d8bb8b9619b0081b26e18eb4d0c5e31`. These are third-party observations;
there is still no UART observation of our own QAxe in this proof. HTTP telemetry,
boot logs and synthetic MUX Stratum fixtures are not ASIC UART captures.

The regressions compile the actual `asic.cpp`, `bm1370.cpp`, `crc.cpp`,
`construct_bm_job`, and its byte-order helpers with only the UART, RTOS, and
logging boundaries stubbed. They produce **synthetic source vectors** for all
16 wire job IDs, four declared ASIC indices, set-address/register-write frames,
and CRC5 inputs of lengths 1 through 31. Synthetic RX trailers are generated by
the actual production C CRC function. Captured bytes are labelled separately
and cross-checked against the C implementation and an independent integer
polynomial implementation. All five have zero residue; all 360 one-bit changes
after their preambles fail. This validates the captured frame format, not our
board or independent work. SHA256d is also cross-checked against OpenSSL on an
explicitly synthetic 80-zero-byte header.

## Interpretations established by source

| Direction | Check or interpretation | Source |
| --- | --- | --- |
| TX | `55 aa`, header, length equal to total bytes minus two | `Asic::send`, `components/bm1397/asic.cpp` |
| TX job | Header bit `0x20` chooses the source sender's CRC16/CCITT-FALSE; initial `0xffff`, polynomial `0x1021`, big-endian trailing checksum | `Asic::send`, `components/bm1397/crc.cpp` |
| TX command | Source CRC5 shift recurrence, trailing five-bit byte | Same sources |
| Known job | Header `0x21`, 82-byte body, one midstate, starting nonce/nBits/nTime/version little endian, two 32-byte ASIC wire fields | `Asic::sendWork`, `sendRawJob`, `BM1368_job` |
| Job ID | TX `(logicalCounter * 24) & 0x7f`; RX `(rawJobByte & 0xf0) >> 1` | `BM1370::jobToAsicId`, `asicToJobId` |
| RX | Exactly 11 bytes, `aa 55`; final-byte bit `0x80` classifies nonce versus register in current source | `Asic::receiveWork`, `processWork`, `asic_result_t` |
| RX CRC | Zero CRC5 residue over all nine post-preamble bytes, including all trailer type and checksum bits | [Pinned Mujina reference](https://github.com/256foundation/mujina/blob/980128574d8bb8b9619b0081b26e18eb4d0c5e31/mujina-miner/src/asic/bm13xx/REFERENCE.md#L333-L352), [codec](https://github.com/256foundation/mujina/blob/980128574d8bb8b9619b0081b26e18eb4d0c5e31/mujina-miner/src/asic/bm13xx/codec.rs#L111-L118) |
| Nonce | Bytes 2..5 interpreted little endian; version bytes 8..9 interpreted big endian, shifted left 13; full version is base version OR returned bits | `Asic::processWork`, `main/tasks/ASIC_result_task.cpp` |
| Register | Bytes 2..5 interpreted big endian; byte 7 is register, byte 6 supplies source address attribution | `Asic::processWork` |
| ASIC index | Nonce address bits `(bigEndianNonce >> 17) & 0xff`, divided by the declared source address interval | `Asic::nonceToAsic`, `chipIndexFromAddr`, `BM1370::init` |
| Header | Version LE, previous-hash bytes, merkle bytes, nTime LE, nBits LE, nonce LE: 80 bytes total | `construct_bm_job`, `test_nonce_value`, `mining_utils.cpp` |

The captured BM1370 trailer has three type bits and five CRC bits. The pinned
reference specifies polynomial `0x05`, initial `0x1f`, no reflection and no
output XOR; its codec validates zero residue across the entire nine-byte suffix.
The checker reports `verified-captured-bm1370-format` or
`failed-captured-bm1370-format` per complete RX frame, and rejects bad CRC
**before** job binding or header validation. Invalid framing leaves CRC
`not-checked-invalid-framing`. This CRC evidence is scoped to the published
11-byte BM1370 format. It does not certify a particular board, unknown response
variant, drain boundary, or isolation mechanism. The firmware decoder remains
unchanged and does not validate RX CRC. The low job-byte nibble is reported
without inventing core-selector semantics.

Capture provenance is documented in [Mujina's source table](https://github.com/256foundation/mujina/blob/980128574d8bb8b9619b0081b26e18eb4d0c5e31/mujina-miner/src/asic/bm13xx/REFERENCE.md#L2258-L2265).
The exact nonce and register bytes come from its [mining-roundtrip fixture](https://github.com/256foundation/mujina/blob/980128574d8bb8b9619b0081b26e18eb4d0c5e31/mujina-miner/src/asic/bm13xx/test_data.rs#L203-L210)
and [response tests](https://github.com/256foundation/mujina/blob/980128574d8bb8b9619b0081b26e18eb4d0c5e31/mujina-miner/src/asic/bm13xx/response.rs#L211-L363).

The CRC5 implementation's eight-bit bit-count wraps for input lengths above
31 bytes. Current two- and six-byte command payloads use four- and eight-byte
CRC inputs. The checker deliberately leaves longer command CRCs unverified.
It does not guess a corrected hardware algorithm.

Unknown job headers such as `0x31` can have their framing and TX checksum
checked, but receive no job-payload or targeting interpretation. An addressed
`0x41` register command is labelled a register write, never targeted work.

## Closed capture schema

The root has these required keys:

| Key | Value |
| --- | --- |
| `captureVersion` | Integer `1` |
| `provenance` | `"observed"` or `"simulated"`; author declaration, never attested by the tool |
| `asicModel` | `"BM1370"` |
| `attribution` | `null`, or the object below |
| `works` | At most 16 work-template objects |
| `events` | 1..4096 framed packet events, in nondecreasing timestamp order |

Optional root keys are `deviceBinding` and `negativeControl`; either may be
`null`. Unknown keys, duplicate JSON keys, nonfinite numbers, booleans in
integer fields, invalid hex, and input files larger than 2 MiB are rejected.
Hex must be lowercase, complete bytes without spaces. Labels are printable
ASCII, 1..64 characters unless stated otherwise.

Attribution is an explicit declaration, not device discovery:

```json
{"mode":"nerd-bm1370-v1","addresses":[0,64,128,192],"source":"observed-enumeration"}
```

`source` is `observed-enumeration`, `source-inferred`, or `simulated`. Simulated
captures cannot claim observed enumeration. One through eight addresses are
accepted only if they equal the current source's enumeration: spacing is
`256 / nextPowerOfTwo(count)`, starting at zero. Out-of-range decoded indices
are reported, rather than assigned to another chip. Use `null` when enumeration
is unknown; the tool then omits attribution. Even `observed-enumeration` is a
capture-author declaration until separately reviewed against actual evidence.

`deviceBinding`, when supplied, has four required nullable fields:
`firmwareSha256` (32-byte hash), `sourceRevision`, `boardProfile`, and
`pcbRevision`. Optional `configurationBefore`/`configurationAfter` each contain
positive uint32 `frequencyMHz`, `coreVoltageMilliVolts`, and `vrFrequencyHz`.
They record declared settings, not measurements. No device identity or image
hash is attested by this offline parser.

Each work template has exactly these required fields:

```json
{"id":"A","headerHex":"<160 lowercase hex characters>","versionMask":536862720,"ticketDifficulty":"1"}
```

`headerHex` is an explicit canonical serialized 80-byte **template**, with the
base version. Bytes 4..75 are immutable for candidate matching. Its final four
bytes are ignored when binding a starting nonce, because these are replaced by
each response nonce. `versionMask` is uint32. `ticketDifficulty` is an exact
positive decimal **string**, at most 64 characters, with decimal magnitude
`1e-64` through less than `1e65`. This is the declared ASIC ticket threshold,
not a guessed pool or network difficulty. Optional uint32 fields are
`startingNonce` (default zero), `requiredVersionMask`, and
`requiredVersionValue` (both default zero). Required value bits must fit their
mask. There is no coin-name, hostname, BTC, or node-tip inference.

A TX event has `type: "tx"`, `atUs` (integer 0..2^63-1), and `packetHex`
(1..255 bytes). A bound job additionally supplies `work` and positive integer
`generation` (at most 2^63-1). Optional uint32 `logicalJobCounter` checks the
exact logical-to-wire mapping. A work is bound only after framing, checksum,
known header, 82-byte body, source ID mapping, one midstate, and every immutable
job field agree. ASIC wire previous-hash/merkle fields reverse the order of
eight four-byte words relative to canonical header fields, keeping bytes within
each word; the actual constructor is cross-tested for this transformation.

An RX event has `type: "rx"`, `atUs`, and `packetHex`. RX packets must be
exactly 11 bytes to be decoded. Optional `candidateHeaders` has at most 16
objects of `{ "work": "A", "headerHex": "<160 lowercase hex characters>" }`.
No candidate means an explicit skipped hash check. The tool neither creates
missing header fields nor reconstructs Stratum coinbase/merkle data.

Candidate checking requires the exact nonce, base version OR returned version
bits, all immutable header bytes, negotiated/required version constraints, and
a matching prior TX wire-ID binding. It independently computes SHA256d and
compares the little-endian hash integer to the supplied ticket threshold.
The displayed difficulty is **Bitcoin-reference bdiff** (`0x00000000ffff...`
divided by that integer), not a claim about an alternative chain's node units
or network validity. A response may match a candidate despite generation
ambiguity; the ambiguity remains explicit.

The RX wire format carries no software generation. Reusing a wire ID for a
different work **or generation** makes later responses ambiguous for the rest
of that capture; the checker does not resolve this using the most recent TX or
an invented drain interval. Split captures only when an independently reviewed
drain/reset boundary justifies doing so.

An ambiguous response reports the full `candidateCount`, an insertion-order
preview of at most **eight** `candidates`, and `candidatesTruncated`. All prior
bindings are still retained internally for ambiguity and header checks and
remain visible in the earlier TX event records. A truncated preview never
resolves ambiguity or discards a later work from header validation. The preview
prevents copying the entire history into every response: the 4096-event
regression with 2048 reused-ID generations followed by 2048 responses produces
16,384 preview entries rather than 4,194,304 history entries, and its formatted
report remains below 12 MiB. Header validation uses a separate at-most-16-work
membership set rather than repeatedly traversing every generation.

## Broadcast negative control

Optional `negativeControl` has exactly seven keys:

```json
{
  "firstWork":"A",
  "secondWork":"B",
  "secondTxEventIndex":1,
  "windowStartUs":1000000,
  "windowEndUs":2000000,
  "minPerAsic":1,
  "drainBasis":null
}
```

Use two distinct known work IDs, a validated first-work TX before the chosen
second-work TX event, distinct wire IDs, an explicit post-dispatch window, and
positive `minPerAsic` at most 4096. `drainBasis` is a nullable printable label
at most 256 characters describing external evidence; the tool never verifies
it. Timestamps are capture-relative microseconds, not wall-clock claims.

The report counts uniquely source-bound second-work responses for every
declared ASIC, separately counting those with explicit header/ticket checks.
Enough responses on every declared chip are **consistent with chain
broadcast**. Missing responses, invalid cutover, reused wire IDs, or unknown
enumeration give an inconclusive result. Other-work, ambiguous, and unbound
responses in the window are counted separately. Silence never proves work
exclusion. `evidenceKind` keeps simulated fixtures separate from self-declared
observations.

Still missing for our QAxe hardware qualification: raw ordered UART TX/RX observations,
exact firmware image and PCB/revision binding, observed chip enumeration,
an actual-board check of this captured-format checksum, a proven job-acceptance
mechanism, and reviewed drain/job-ID reuse evidence. This parser provides no
substitute for those inputs and always reports `isolationVerified: false`.
